| DL-033 | What a review verdict is anchored to | The commit SHA / the change / the author's word | **A verdict is anchored to the change, not to the commit that carries it.** A `VERDICT:` review posted at SHA `X` carries to `X'` only when all four hold, each recorded in the merge comment by R1: (1) the changed-file list is derived, never typed — `gh pr diff <N> --name-only` at `X` — and is non-empty, with every path present at `X` (`git ls-tree -r --name-only X -- <paths>`), because an empty diff over a mistyped path also exits 0 and proves nothing; (2) `git diff X X' -- $(gh pr diff <N> --name-only)` is empty; (3) every path in `git diff --name-only X X'` also appears in `git diff --name-only <old-main-tip> <new-main-tip>`, so the update is a strict subset of main's advance and a commit outside it fails; (4) checks are green on `X'`. Both SHAs and both main tips go in the merge comment, and `git diff X' <squash-commit>` must be empty after merge, proving that what landed is what was verified. Any non-empty result invalidates the verdict and the PR goes back for review. Why: with strict up-to-date, a shared identity and three lanes, both PRs open at the time needed a re-pin, and 22 of M0's 38 turns were review verdicts (ledger U9). The alternative — dropping strict — would stop the checks from running against current `main`, which is the guarantee worth keeping.
